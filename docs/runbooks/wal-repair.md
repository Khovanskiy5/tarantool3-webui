# Runbook: WAL repair (восстановление повреждённого xlog)

Когда xlog-файл обрезан или имеет битую контрольную сумму — applier останавливается посреди replay, `box.info.status` зависает на `orphan`/`loading`, в логах что-то вроде `xlog.c:… invalid …`. Чинится на странице **/cluster-recovery** (визард «WAL repair»). Роль — `admin`.

> ⚠️ Диагностика и quarantine видят **только локальный** `wal_dir` того инстанса, который обслуживает запрос. Повреждённый узел обычно лежит (orphan/loading) — подключайся к НЕМУ и целься в него.

## Хвостовое vs серединное повреждение

Это главное различие, определяющее риск:

- **Хвостовое** (битый файл — **последний** в цепочке по LSN): теряется только неподтверждённый хвост (torn write при падении). Класс **caution** — штатно восстановимо.
- **Серединное** (за битым файлом есть хорошие xlog'и): пропуск/обрезка этого файла **отрезает всю цепочку после него** — теряются подтверждённые транзакции. Класс **dangerous**.

`force_recovery = true` пропускает битые записи xlog и читает сколько может, но **НЕ лечит повреждение снапшота / системных спейсов** — такое восстанавливается только через rebootstrap, не через force_recovery.

## Как читать панель оценки

Открыв визард, ты увидишь **сводку оценки** (preflight), посчитанную бэкендом по живому состоянию:

- **Бейдж риска** — `caution` (хвост) или `dangerous` (середина).
- **Effects** — что именно произойдёт (rename файла в `.corrupt`, пропуск на следующем бутстрапе).
- **Preconditions** — чек-лист (файл присутствует в локальном `wal_dir`; для опасного — пауза/бэкап/фиксация состояния).
- **Manual recovery** и **Failure commands** — рекомендации и готовые команды (см. ниже).

Для **caution** — одна кнопка Apply. Для **dangerous** — нужно отметить acknowledge и впечатать токен `WAL <file>`; сервер откажет в применении без подтверждения и выполненных предусловий.

## Порядок (рекомендуемый)

1. **Сначала бэкап.** Rename `.xlog → .corrupt` — это НЕ бэкап. Сними отдельную байтовую копию файла (а лучше всего `wal_dir`/snap):
   ```bash
   docker cp webui-tt-2:/opt/webui/var/lib /backup/wal-tt-2-$(date +%s)
   ```
2. **Диагноз** — визард «WAL repair» → список xlog с пометкой good/BAD и `last_lsn` (последний валидный LSN = граница хорошего префикса).
3. **Предпочти rejoin от здоровой реплики локальному quarantine.** Если есть достижимый пир с vclock ≥ твоего — это **zero-loss** путь: вместо quarantine сделай rebootstrap узла от живого пира ([divergent-rejoin / rebootstrapInstance](failover-issues.md#divergent-rejoin)). Локальный quarantine — только когда здоровой реплики нет.
4. **Если реплики нет — quarantine** битого файла (rename в `.corrupt`), затем подними инстанс с `force_recovery = true`.
5. **Финализация:** после успешного форс-старта сделай запись в БД и `box.snapshot()`, затем **выключи** `force_recovery` обратно — иначе следующий обычный рестарт снова упрётся в файл, а оставленный флаг замаскирует будущие повреждения.

Эквивалент через GraphQL (диагностика — read-only, проходит без подтверждения):

```graphql
mutation { recoveryAction(action: "wal_diagnose")
  { ok results { peer ok msg } } }
# quarantine опасного файла — потребует acknowledge/confirmToken через панель
mutation { recoveryAction(action: "wal_quarantine",
  payload: "{\"file\":\"00000000000000000178.xlog\"}")
  { ok results { peer ok msg } } }
```

## Команды для разбора

```bash
# найти границу хорошего префикса в файле (последний валидный LSN)
docker exec webui-tt-2 tarantoolctl cat <wal_dir>/00000000000000000178.xlog | tail
# загрузиться мимо битой записи (потом box.snapshot() и вернуть флаг в false)
#   в конфиге инстанса: force_recovery = true
```

> Пропуск/обрезка записей может оставить данные **логически несогласованными** (поздние записи ссылаются на пропущенные). Для серединного повреждения это ожидаемо — оцени объём потери по `last_lsn` и vclock пиров перед quarantine.
